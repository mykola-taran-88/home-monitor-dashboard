# Валідація щодо технічного завдання

**Дата перевірки:** 27 жовтня 2026 року  
**Обсяг:** консолідоване ТЗ Home Monitor (Home, Climate, Energy, Weather), наданий Worker `index.js` і вихідний комплект проєкту.

## Висновок

Реалізацію перевірено та відразу виправлено на рівні коду. Це **часткова відповідність ТЗ, а не повністю закриті acceptance criteria**: локальні тести підтверджують збірку, статичні контракти та поведінку HTTP Worker, але для деяких вимог потрібні реальні API-дані, а для візуальних/інтерактивних критеріїв — браузерний тест. Реальний backend не викликався; розгортання у Cloudflare не виконувалось.

## Статус по доменах

### Home — частково реалізовано

**Підтверджено кодом:** score береться з API, null відображається як відсутнє значення, активні події обмежені двома записами, рекомендації — трьома, є deep links, окремі сторінки помилок/порожніх даних і статуси джерел.

**Не доведено повністю:** детермінована дедуплікація однакової першопричини залежить від стабільних `entity_id`/`id` у API; повне збереження останніх успішних payload при всіх видах збоїв не перевірене на реальному backend; повноцінний аудит WCAG і збереження scroll/back-forward у браузері не пройшли E2E.

### Climate — частково реалізовано

**Підтверджено кодом:** векторний SVG з п’ятьма внутрішніми кімнатами, зовнішній сенсор не додається до кімнатного плану, базовий `viewBox`, режими заливки, label для кімнати без сенсора, два окремі графіки, адаптивні Y-діапазони, comfort bands, розриви при null (`spanGaps:false`), period/room preference persistence і abortable history load.

**Не доведено повністю:** реальний click/keyboard/pinch/pan/fullscreen, автоматичне визначення кімнати з найбільшим відхиленням, точна тотожність часу/таймзони в API та hover-поведінка на реальних наборах даних; геометрія плану схематична, оригінальний архітектурний кресленик не був наданий окремим векторним файлом. Комфортні межі залежать від конфігурації backend, інакше використовуються типові межі з ТЗ.

### Energy — частково реалізовано

**Підтверджено кодом:** початковий режим потужності/доби, режими power/energy/cost/voltage, null-safe форматування, тарифні фони лише при наданій конфігурації, stacked day/night серії коли API повертає обидва сегменти, фактичні й прогнозні показники окремі за наявності відповідних полів.

**Потрібне допрацювання/підтвердження:** розбиття інтервалу, що перетинає межу двох тарифів, не можна гарантувати без timestamp/raw intervals або готових backend `day_*`/`night_*` значень. Порівняння з попереднім ідентичним періодом, voltage threshold bands лише за конфігурацією, точний marker peak, budget-vs-forecast-vs-actual і тарифні підсумки треба прогнати з фактичними API payloads. Не можна надійно підрахувати вичерпні значення без backend schema.

### Weather — частково реалізовано

**Підтверджено кодом:** current weather перед 48h-графіком, змішаний режим температури й опадів, шкала опадів у %, погодинна стрічка, до семи прогнозних карток зі спільним температурним масштабом, wind gusts/direction коли наявні, day/night background на основі джерела, погодний warning не вигадується, вентиляційна рекомендація пригнічується за активного попередження.

**Не доведено повністю:** точне відображення часу сходу/заходу по міжточкових координатах; поведінка при часовому поясі, відмінному від API/config; клік по прогнозному часу і синхронна лінія курсора у реальному Chart.js; коректність усіх полів для конкретного провайдера, тому що реальні payloads не надані.

## API-залежності, які не можна безпечно «виправити» лише у фронтенді

- Енергетичний backend має повертати tariff schedule + timezone + rates, або денні/нічні значення на кожен aggregation interval. Фронтенд не вигадує ці години й суми.
- Climate API має повертати стабільні room/device mappings, timestamps зі зрозумілою timezone та null для пропусків.
- Weather API має повертати location timezone, forecast timestamps, daily sunrise/sunset та реальні weather warnings; відсутність значення не означає нуль.
- Для відмінності `offline`, `stale`, `disabled`, `archived`, `no-history`, `not-configured` потрібні нормалізовані статуси та timestamps.

Деталі endpoint/field gap див. у [`api-gaps.md`](api-gaps.md).

## Як відтворити локальну перевірку

```bash
npm run check
npm test
npm run typecheck
```

На дату цього звіту `npm test` містить 13 тестів: 8 статичних acceptance/regression перевірок за ТЗ і 5 Worker HTTP smoke/security тестів. Це не 13 повних UI E2E сценаріїв. Headless Chromium у цьому середовищі блокує і `http://localhost`, і `file://` з `ERR_BLOCKED_BY_ADMINISTRATOR`, тому реальна браузерна/візуальна перевірка не зараховується.
